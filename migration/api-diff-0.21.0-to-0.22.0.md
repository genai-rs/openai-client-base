# openai-client-base 0.21.0 → 0.22.0: a new value no longer fails a response

This release generates with `timvw-rust` 0.13.1 and its `openEnums` option (Milestone 3.5 of the
[generator design](https://claude.ai/artifact/ABar8Up91gjVMDHgHL1GE3)). The OpenAI spec is unchanged. An enum or tagged
union that a response or webhook can hold gets a catch-all variant for values the spec does not list. The
machine-readable census is `api-diff-0.21.0-to-0.22.0.json` in this folder.

## Why

The API can send a value before the spec, and so this crate, lists it. Enums were closed, so one new value anywhere, such
as a new `finish_reason` or a new `type` on a tool call, turned the whole response into a `serde_json` error. The rest of
the response was lost with it, and the only fix was a new release of this crate.

## What stays the same

- Everything that exists keeps its name and type. No field, function, derive or model is added, removed or changed.
- Known values decode and serialize as before. `src/apis` is unchanged.
- Enums keep `Copy`, `Eq`, `Hash` and `Ord`.
- `FromStr` and `TryFrom` accept exactly the strings they accepted before.
- A value of another JSON kind is still an error: a number for a string enum, or a missing, `null` or non-string tag on a
  tagged union. A known tag with a broken body is still that variant's error, not `Unknown`.

## What changes

The diff against the previous release only adds these, in 1,238 files:

- 1,265 enums gain a variant: 1,260 `Unknown`, 4 `UnknownValue` and 1 integer `Unknown = i64::MAX`, each with
  its `serde` attribute, doc comment and `Display` arm.
- 142 tagged unions gain `Unknown(serde_json::Value)` with a `Display` arm, and their dispatch returns it for a tag they
  do not know, in place of the error.
- `unknown_tag` in the private `union_dispatch` module gets `#[allow(dead_code)]`. It is still used by the unions that
  stay closed.

### What opens

Everything a response body can hold, in any media type and of any status, so server-sent events and error bodies count,
and what a webhook delivers. Types behind a `serde_json::Value` count too (`OutputItem`, `ResponseStreamEvent`), since you
can decode them yourself. A type that requests also use counts.

| | Total | Open | Closed although a response can hold it | Not reached by a response or webhook |
| --- | --- | --- | --- | --- |
| Value enums | 2,072 | 1,265 | 43 | 764 |
| Tagged unions | 246 | 142 | 2 | 102 |

The 163 untagged unions do not change.

### What stays closed, and why

**Decoding in order relies on enums rejecting values.** An untagged union tries its variants in turn, as do the variants
of a tagged union that share a tag value, and an enum is often what makes an earlier variant step aside for a later one.
A catch-all there would change what known input decodes to, so these 43 enums and 2 unions stay closed:

- An enum in front of a free string. `ImagesResponseSize` is `TextVariant(ImagesResponseSizeTextVariantEnum)` or
  `Text(String)`, and `"1536x864"` must stay in the string instead of becoming `Unknown` and losing the value.
- A `role` that tells two structs apart, such as `InputMessage.role`. The struct's other fields are free to open.
- Anything in a struct in front of a map or a `Value`, and a tagged union in front of a struct whose tag is free, such as
  the union `InputContent`, `InputTextContent.type` and `ImageDetail`.

The decision is per enum, so a component enum guarded in one union is closed wherever else it is used. A new value in
one of these goes on to the later variant if there is one. **If nothing takes it, it still fails the decode, as it did
before.** `ImageDetail` is the one you are most likely to meet, since `detail` is a required field of
`InputImageContent` and `ComputerScreenshotContent`.

**What no response can hold.** These 764 enums and 102 unions are what only requests use (`AudioResponseFormat`,
`ChatCompletionRequestMessage`), which is your own input, and types no HTTP operation or webhook reaches. The latter are
above all WebSocket-only Realtime, Live and Responses types: `LiveServerEvent`, `RealtimeTranslationServerEvent`,
`ResponsesServerEvent` and what they hold. If you decode these yourself from a WebSocket, a new event type is still an
error. The Realtime and Live types that an HTTP operation or webhook does return, such as
`RealtimeSessionCreateResponseGa` and `WebhookRealtimeCallIncoming`, are open.

### What `Unknown` does on an enum

| | `Unknown` |
| --- | --- |
| Decoding | Any string the enum does not list. serde also reads an object with one key as an enum, so `{"new": null}` is `Unknown` as well. |
| `Serialize` | `"unknown"`. The original string is gone. |
| `Display` | `unknown` |
| `FromStr`, `TryFrom` | Never produce it. `"unknown"` and any other unlisted string are an error, because parsing is a strict check of what a caller typed. |

- **The value is not kept.** Sending a decoded `Unknown` back does not send what the API sent. It sends `"unknown"`,
  which no enum lists, so the API rejects it instead of reading another value into it. This matters for enums that
  requests also use, such as `ServiceTier`, and for structs you copy from a response into a request.
- All unlisted values are one variant, so two different new values compare equal, and `Unknown` sorts after the listed
  variants. The decoded type does not tell you which value came.
- `MessageRole`, `BetaMessageRole` and the `ModerationStage` of `ImageGenToolCallModerationDetails` and
  `BetaImageGenToolCallModerationDetails` list `unknown` themselves. That value keeps the variant `Unknown` and still
  parses from `"unknown"`. Their catch-all is `UnknownValue`, which serializes and displays as `unknown_value`, and
  `FromStr` never produces that either.
- The one integer enum, `pcm_audio_format::Rate`, has `Unknown = i64::MAX`, which is also what it serializes to.
  `Display` prints `unknown`.

### What `Unknown(Value)` does on a tagged union

- It holds the JSON as it came, tag included, so it serializes back to the same JSON and sending it back is faithful.
- `Display` prints that JSON.
- Most unions have the tag `type`. `AssistantStreamEvent` and a few others use `event`, `object` or `action`.
- A union with a branch called `Unknown` would use `UnknownValue(Value)`. No union in this release does.

## Migrating

- **An exhaustive `match` without a wildcard no longer compiles** (`E0004`) on any of these types: add an arm. Prefer naming
  `Unknown` to writing `_`, so the compiler still points you at the next known variant. As today, any enum can gain
  variants in a later release when the spec adds one: these types are not `#[non_exhaustive]`.
- Decide what `Unknown` means at each site. Don't map it onto a listed value, or onto `None` where `None` means the field
  was absent. A `finish_reason` that came back as `Unknown` still means the choice finished.
- Reading a tool call or an event: `ChatCompletionMessageToolCallsInner::Unknown(value)` and the like hold the JSON, so
  `value["id"]` works without a release of this crate.
- Code that relied on a decode error to notice a new value: check for `Unknown` instead. A response that used to fail now
  arrives.
- **Validating text with `serde_json::from_str::<SomeEnum>` no longer rejects anything on an open enum.** Use
  `"text".parse::<SomeEnum>()`, which stays strict.
- Don't send a decoded `Unknown` of an enum back to the API. Handle it before building the request.
- Code that matched the error text `unknown ... value` from a union: the error is gone for the open unions, and they return
  `Unknown(Value)`.
